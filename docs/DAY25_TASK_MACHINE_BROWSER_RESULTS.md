# День 25 — проверка браузерного автопилота Task Machine

Дата проверки: 4 октября 2026 года.

## Цель

Проверить через реальный браузерный интерфейс, а не через прямые HTTP-вызовы,
что режим `Автопилот · продолжать самостоятельно`:

1. принимает решение о переходе только после независимой проверки ответа;
2. сам применяет разрешённое событие Task Machine;
3. создаёт handoff между этапами;
4. сам отправляет продолжение следующего этапа;
5. способен пройти цепочку `planning → execution → validation → done`.

Проверка выполнена через встроенный браузер Codex на локальном Flask-приложении.
Использовались реальные платные вызовы DeepSeek. MCP были принудительно отключены.
Локальная embedding-модель работала в offline-режиме; документы в Hugging Face не
отправлялись.

## Сценарий 1 — Task Machine вместе с RAG

### Задача

Подготовить справку по документам базы знаний о формировании выборки российских
ПИФов и ограничениях результата. Требовались источники и цитаты.

### Что сделал браузерный автопилот

| Шаг | Результат |
|---|---|
| Стартовый ответ planning | Независимая проверка приняла ответ: `stage_complete=true`, рекомендовано `approve_plan` |
| Переход | Браузер сам отправил событие `approve_plan` |
| Handoff | Создан handoff `planning → execution` с планом, решениями, ограничениями и критериями готовности |
| Продолжение | Браузер сам отправил служебное сообщение `[Автопилот] Продолжи задачу...` |
| Execution | Ответ не был признан завершённым; автопилот корректно остановился на `execution` |

Финальное состояние диалога: `execution`.

### Почему сценарий остановился

Автоматический маршрутизатор выбрал маршрут `task`. Поиск по индексу при этом
выполнился (`20 → 5`, максимальная similarity `0.8393`), но найденные чанки были
использованы только для маршрутизации: `chunks_used_for_answer=false`,
`route_probe_only=true`.

Поэтому execution-модель получила Task State и handoff, но не получила тексты
документов. Она правильно отказалась придумывать методику и цитаты и запросила
доступ к базе. Независимый валидатор оставил `stage_complete=false`, поэтому
автопилот не сделал недопустимый переход `complete_execution`.

Это не поломка переходов Task Machine. Это дефект интеграции автоматических
продолжений с маршрутизатором: задача одновременно требует Task State и RAG,
но запрос `[Автопилот] Продолжи задачу...` классифицируется как чистый `task`,
а не как сочетание `task + rag`.

Технический идентификатор диалога:
`a2ddf5ff2f1c40f88ee55aff20b8dc8e`.

Расход основного/проверочного контура DeepSeek: 7 874 токена. В этом проекте
`usage.total_tokens` уже включает генерацию ответа этапа и независимую проверку,
поэтому их нельзя складывать повторно.

## Сценарий 2 — контроль Task Machine без зависимости от документов

### Задача

Составить и проверить памятку ровно из трёх пунктов:

1. переход выполняется только после принятой проверки этапа;
2. каждый переход создаёт handoff;
3. статус `done` разрешён только после этапа `validation`.

Итог требовался текстом в чате, без создания файлов. RAG-переключатель оставался
включённым, но маршрут был `task`, а найденные чанки использовались только как
route probe и для ответа не требовались.

### Фактическая цепочка

| Время | Этап | Ответ проверки | Автоматическое событие | Следующий этап |
|---|---|---|---|---|
| 16:38:58 | planning | `stage_complete=true` | `approve_plan` | execution |
| 16:39:07 | execution | `stage_complete=true` | `complete_execution` | validation |
| 16:39:15 | validation | `stage_complete=true` | `pass_validation` | done |

Все три перехода имеют `source=autopilot`. Для каждого перехода создан новый
`stage_run_id` и отдельный структурированный handoff:

- `planning → execution`;
- `execution → validation`;
- `validation → done`.

После `approve_plan` и `complete_execution` браузер сам добавил пользовательские
служебные сообщения `[Автопилот] Продолжи задачу...`. После `pass_validation`
сервер сформировал финальный ответ этапа `done`; новых переходов больше нет.

Финальное состояние диалога: `done`.

Технический идентификатор диалога:
`3b7de9ed596343b598cea43cdc4dbc27`.

Расход основного/проверочного контура DeepSeek: 18 736 токенов. Отдельный вызов
LLM-маршрутизатора: 611 токенов. Итого для контрольного сценария: 19 347 токенов.

## Итог

Браузерный автопилот Task Machine работоспособен: он самостоятельно прошёл весь
жизненный цикл `planning → execution → validation → done`, применил только события,
разрешённые независимой проверкой, сохранил три handoff и не потребовал ручных
нажатий между этапами.

Одновременно обнаружена конкретная интеграционная проблема для задач с RAG:
автоматическое продолжение не наследует документальную потребность исходной задачи.
Маршрут `task` сохраняет цель и handoff, но не передаёт найденные чанки в execution.

Рекомендуемое исправление: при автоматическом продолжении учитывать не только
текст служебного сообщения, но и зафиксированные требования задачи/плана. Если в
них требуются документы, источники или цитаты, маршрут должен быть составным
`task + rag`, а найденные чанки должны добавляться к контексту ответа. При этом
Task State и handoff остаются обязательной частью запроса.

### Статус исправления

Исправлено после прогона. На этапах `execution` и `validation` автоматическое
продолжение теперь проверяет описание задачи, план и активные handoff. При явной
документальной зависимости выбирается маршрут `rag`, а поисковый запрос строится
из авторитетного состояния задачи вместо общей служебной фразы. Task State и
handoff по-прежнему передаются тому же вызову. Поведение закреплено профильным
автоматическим тестом без платного API-вызова.

## Служебные замечания о запуске

Перед успешной проверкой были два неуспешных подготовительных запуска:

1. библиотека embedding-модели пыталась проверить Hugging Face; запуск повторён
   с `HF_HUB_OFFLINE=1` и `TRANSFORMERS_OFFLINE=1`;
2. Flask-процесс без сетевого разрешения не мог обратиться к DeepSeek; сервер
   перезапущен с разрешённым сетевым доступом.

Эти попытки не меняли код проекта и не являются результатом проверки логики
автопилота.
